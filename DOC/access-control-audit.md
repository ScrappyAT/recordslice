# Access control audit

Every row below is a real HTTP request, made with `curl` against a production build
(`next build` + `next start`, `localhost:3000`) and a live Postgres database, not
reasoned about. Every attempt is listed whether it succeeded or failed - the point of
this table is what was tried, not only the outcome.

## Setup

Two real accounts, created through the actual sign-up and verification API - not
seeded, not inserted directly:

1. `POST /api/auth/signup` with a real email/password/name.
2. The verification code read from the server's console log (`lib/email.ts` prints
   instead of sending, per Assessment 1's design - nothing about receiving the code
   is faked).
3. `POST /api/auth/verify` with that code, which returns a real session cookie.
4. Two invoices each, created through `POST /api/invoices` with that cookie - the
   real create flow, not a database insert.

**One exception to "not constructed by direct insert":** the `emailVerifiedAt is null`
test rows below use a third account built by hand -
```
email: audit-unverified@example.com, emailVerifiedAt: null, with a live Session row
```
This is deliberate and named in `AGENTS.MD`'s own Status codes section: the real
sign-in/verify flow can never produce a session for an unverified user (sign-in refuses
one, verification sets the field in the same request it creates the session), so the
only way to test the 403 path at all is to construct the state directly. It carries no
invoices and is not a stand-in for either real account.

`NEVER = 99999999999999999999999999999999` - a 32-character hex-shaped string that was
never generated by `lib/ids.ts`, used for the "never existed" rows.
